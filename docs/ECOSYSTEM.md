# 生態定位：與 jagua-rs / sparrow 的關係

**記錄日期**：2026-09-09
**結論先行**：閉門造車確實不明智，而且我上一輪的市場分析有一個**具體的事實錯誤**需要更正。

---

## 1. 上一輪報告的更正

我在 `KERNEL.md` 與 `ROADMAP.md` 寫過：

> jagua-rs 自陳設計哲學是「always err on the side of caution」——
> 兩物體極近時寧可誤報碰撞

這句話**方向正確但精度不足**。實際查證原始碼後，真實情況是：

**jagua-rs 的生產謂詞用的是 `f32`，不是 `f64`。**

證據（`jagua-rs/src/collision_detection/quadtree/assertions.rs:19`，原始註解）：

```rust
/// Recomputes the segment-rectangle intersection in `f64` so assertions do not inherit
/// conservative rounding from the production `f32` predicate.
```

也就是說：**他們自己已經知道 f32 謂詞有保守捨入問題，所以在斷言層改用 f64 重算。**
`jagua-rs/src/util/fpa.rs` 則是 `FPA(pub f32)` + `float_cmp::approx_eq!` 的容差比較封裝。

`jagua-rs/src/geometry/` 全域幾乎不用 f64（`transformation.rs` f32×15 / f64×0，
`shape_modification.rs` f32×9 / f64×2）。

---

## 2. 實測：f32 謂詞的錯誤率

以精確有理數（f32 皆為二進位有理數，用 i128 定點或 Python `Fraction` 展開）為真值。

| 測試組 | 樣本 | **f32 謂詞誤判** | **f64 算 f32 輸入誤判** |
|---|---|---|---|
| 整數格座標 ±1000 | 400,000 | 0 | 0 |
| 全尾數 f32 ∈[1,2) 隨機 | 500,000 | 0 | 0 |
| **近共線・全尾數 f32** | 500,000 | **49,820（9.96%）** | **0** |
| **Cassini 恆等式（f32）** | 36 | **18（50%）** | **0** |

**近共線情形下 f32 謂詞每 10 次錯 1 次。** 這正是 nesting 的核心工況 ——
零件緊貼排列時，邊與邊就是近共線。

---

## 3. 為什麼 f64 在此「足夠」——以及它何時不夠

f32 尾數 24 bit。`orient2d` 是次數 2 的謂詞：
差 `b−a` 在 f64 中精確（24 bit 輸入，指數跨度小時無捨入），
積約 48 bit < 53，最終減法在多數情形亦精確。

實測 f64 對 f32 輸入的誤判率在以下攻擊下**全部為 0**：

| 攻擊 | 樣本 | f64 誤判 |
|---|---|---|
| 指數跨度 2^0…2^28 近共線 | 200,000 ×8 檔 | 0 |
| 大值 + 微擾（差需極多位元） | 500,000 | 0 |
| 跨尺度近共線 | 1,140,000 | 0 |
| 近上溢 2^127 乘積 | 100,000 | 0 |

### f64 真正的失效邊界：指數跨度 ≥ 2^53

| 座標指數跨度 | f64 誤判率 |
|---|---|
| 2^20 | 0 / 20,000 |
| 2^40 | 5 / 20,000 |
| **2^53** | **20,000 / 20,000（100%）** |
| 2^100 | 20,000 / 20,000 |

**機制**（已逐步驗證）：

```
a = 1.5×2^100, b = 1.3×2^-130
f64:  b[0] - a[0]  ==  -a[0]     ← b 被完全吸收
      行列式 = 0.0  → 判定「共線」
精確: 行列式 > 0    → 實際不共線
```

指數跨度超過 53 時，減法把小項整個吃掉，行列式退化為 0。

**結論**：對 nesting 這種**座標量級同質**的工況（一張料板上的零件，
座標跨度遠小於 2^53），**f64 對 f32 輸入是精確的**。
本專案的 i128 精確謂詞在此**沒有必要** —— 這點必須誠實說明。

## 4. 對本專案定位的影響

### 4.1 上一輪的 Phase 8B（做一個「精確版 nesting 引擎」對打 jagua-rs）是錯的

理由：

1. jagua-rs 的差距**不需要 i128 就能補**。把 f32 謂詞換成
   f64 計算，實測誤判從 9.96% 降到 0，成本只有 **1.21×**
   （f32 1.97 ns → f64 2.38 ns，均含 `black_box`）。
2. 從零做一個 nesting 引擎去對打一個有 581 commits、190 stars、
   13 個 release、活躍維護（最近提交 2026-09-07）、且**已是學術 SotA**
   的專案，是把 12 個月投進一場沒有勝算的仗。
3. 難點本來就主要在 NP-hard 組合最佳化，不在幾何。

### 4.2 正確的做法：貢獻，不是競爭

`jagua-rs` 授權為 **MPL-2.0**（檔案級 copyleft，商業可用），
接受 PR（近期 #85、#89 皆為外部合併），且作者有 GitHub Sponsors / Buy Me a Coffee。

可提交的具體貢獻，全部有本專案已驗證的量測支撐：

| 貢獻 | 依據 | 成本 |
|---|---|---|
| 近共線 f32 誤判的**再現測試集** | 49,820/500,000 實測 + Cassini 構造 | 低 |
| 關鍵謂詞改以 f64 計算 | 誤判 0，代價 1.21× | 低 |
| 指數跨度 2^53 的**文件化界限** | 已逐檔量測 | 低 |
| exact-fit 能力（sparrow 明言做不到） | 需 Tier 0 + 精確路徑 | 中 |

sparrow 論文原話：

> **Exact fits – where moving the position of an item by even the smallest
> representable distance causes a collision – cannot be produced by sparrow.**

這是**論文作者自己標注的能力缺口**，而非我方臆測。這才是本專案真正能補的位置。

## 5. 形式化工作（Lean）的定位

使用者以其他工具產出了 Lean 4 形式化（`1135.md`，10 條定理、
`lean/` 14 模組、無 `sorry`、`lake build` 通過；Rust 側 96 項測試 = 原 77 + 新 19）。

**注意：該 Lean 與 `src/formal.rs` / `tests/formal_lemmas.rs` 目前不在本工作區**，
本倉庫 HEAD (`bd2c743`) 仍為 77 項測試。合併前需先把那些檔案放進工作區。

定位判斷：

- 這批定理（窮舉、良基終止、許可證不變性、合約相容、抽象等價、
  無死鎖、非干擾、精化）是**軟體工程的通用性質**，
  不是幾何謂詞的正確性。它們證明的是「引擎的框架行為」，
  不是「orient2d 的符號正確」。
- 真正能與 `ECOSYSTEM.md` 第 3 節接上的，是 `Mec.lean` 的
  `mec_radius_eq` / `mec_perm` / `mec_unique` —— MEC 的數學契約。
- 對商業化的價值在 **ROADMAP Phase 8C（可驗證幾何）**：
  航太／自駕／醫材認證願意為「形式化證明過的幾何核心」付費，
  市場小但單價高、競爭極少。這比 nesting 更契合已有資產。

## 6. 修訂後的建議路線

1. **短期（數週）**：把第 3 節的量測整理成 jagua-rs 的 issue／PR。
   這是零風險、高可見度的切入 —— 用實測數據建立技術信譽，
   而不是宣稱自己要取代對方。
2. **中期**：以 exact-fit 為題，看能否成為 jagua-rs 的一個
   可選精確後端（feature flag），而非另起爐灶。
3. **長期**：形式化幾何核心（Lean + Rust 雙證據鏈）走認證市場。

**放棄**：Phase 8B 原定的「從零自建 nesting 引擎對打 sparrow」。
